# RAKwireless RUI3 PlatformIO Platform

## Project Overview

Custom PlatformIO platform wrapping the RAKwireless RUI3 BSP repos. Ships as a single repo with all build logic — no forks of upstream RAK repos. Each upstream BSP tag is repackaged once (`tools/bsp.py`) into a framework tarball with a PlatformIO manifest, published as a GitHub release asset of this repo, and referenced by URL from `platform.json`.

Compiler and linker settings are not kept in this repo: the builder resolves the BSP's own Arduino recipes (`platform.txt` + `boards.txt`) at build time, so a new upstream release builds with exactly the flags, include paths and sources the Arduino IDE would use.

## Architecture

- `platform.json` / `platform.py` — PlatformIO platform definition; `platform.py` picks the BSP package for the board's core and resolves local framework tarballs (see Build & Test)
- `boards/` — Board manifests, generated by `tools/boards.py` (one per upstream board)
- `builder/main.py` — SCons entry point (toolchain, ELF → BIN/HEX, size)
- `builder/frameworks/rui3.py` — The one framework script for all MCU families
- `builder/rui3_recipe.py` — Resolves upstream `platform.txt` / `boards.txt` (board props, IDE menus, compile and link recipes) into SCons settings; no SCons imports, also used by `tools/`
- `builder/buildtime.py` — Stamps BUILD_DATE / BUILD_TIME into a copy of the variant's `version.c`
- `builder/nrf52_dfu.py` — nRF52 signed DFU package and serial upload, in pure Python (replaces nrfutil 6.1.7 and RAK's uploader.py)
- `tools/bsp.py` — Repackages upstream BSP tags into framework tarballs (`package`) and points `platform.json` at them (`pin`)
- `tools/bsp_patches.py` — Compatibility patches applied while repackaging
- `tools/boards.py` — Generates `boards/*.json`, the board list in `platform.json`, and `docs/boards.md`
- `examples/` — Example PlatformIO projects (lorawan-otaa, system-info)
- `tests/` — `python -m unittest discover -s tests` (the serial upload tests need pyserial: use PlatformIO's Python, `~/.platformio/penv/bin/python`)

## Conventions

- **Cross-platform paths**: Always use `os.path.join()`, never hardcoded `/` or `\\`
- **Pure Python tools**: No platform-specific executables. All build helpers are Python.
- **No upstream forks**: Build logic wraps the upstream BSP as-is. Fork only as last resort.
- **Upstream is the source of truth for build settings**: never copy flags, defines or include paths into board manifests or the builder. Board manifests only name the upstream board (`build.rui3.board`); anything else that differs from Arduino needs a comment explaining why.
- **Board options**: the Arduino IDE menus are exposed as `board_build.rui3.<menu> = <option id or label>` (case-insensitive, since PlatformIO lowercases option names). Defaults are the first option in `boards.txt`, as in the IDE. `docs/boards.md` lists them per board.
- **One board per product**: `PRODUCTS` in `tools/boards.py` lists every PlatformIO board with its upstream board, name and docs URL. A WisDuo module and the WisBlock Core built around it are separate boards sharing one upstream board (RAK4630 + RAK4631 → `WisCoreRAK4631Board`). Names follow `<part> <family> (<module inside>)`, e.g. `RAK4631 WisBlock Core (RAK4630)`.
- **Board ids are public**: never rename one. A new upstream board needs a `PRODUCTS` entry (the generator warns).
- **Curated board fields** (debug, upload protocols, `build.mcu`) are kept by the generator; edit them in `boards/*.json`, then run `tools/boards.py --check` to confirm the file is stable. Names and URLs are edited in `PRODUCTS`.
- **No SUPPORT_FUOTA on 4.x BSPs**: their FUOTA package files predate the LoRaMac 4.7.0 API. `tools/bsp_patches.py` guards them while repackaging so they at least compile if FUOTA is enabled. (5.x `boards.txt` enables FUOTA itself.)
- **Line endings**: Tracked files use CRLF; keep that when editing or adding files.

## Phased Approach

1. **Phase 1 (DONE)**: STM32WLE / RAK3172 family — builds on 4.3.0: Flash 89.1%, RAM 70.8%
2. **Phase 2 (DONE)**: nRF52 / RAK4631 — builds on 4.3.0: Flash 56.1%, RAM 37.5%
3. **Phase 3 (DONE)**: Apollo3 / RAK11720 — builds on 4.3.0: Flash 29.4%, RAM 39.8%
4. **Phase 4**: Polish, upload support (nRF52 done; STM32 and Apollo3 next, both YMODEM via `uploader_ymodem` upstream), CI/CD, docs, publish (GitHub releases first; PlatformIO registry later)

Known upstream bug: `rak5010` does not compile on 4.2.3 or 4.3.0, in the Arduino IDE either (`LoRaMac.c` uses `NUM_OF_KEYS`, which only exists with `SOFT_SE`, and RAK5010 does not define it).

## BSP Packages (all at v4.3.0_400)

Platform version mirrors RUI3 major.minor (platform 4.3.x ships RUI3 4.3.0). Framework package versions are `X.Y.Z+BUILD` (e.g. `4.3.0+400`), because several upstream builds share one X.Y.Z.

- `framework-rui3-stm32wle` ← `RAKWireless/RAK-STM32-RUI` tag `v4.3.0_400`
- `framework-rui3-nrf52` ← `RAKWireless/RAK-nRF52-RUI` tag `v4.3.0_400`
- `framework-rui3-apollo3` ← `RAKWireless/RAK-APOLLO3-RUI` tag `v4.3.0_400`

Assets live at `https://github.com/RAKWireless/platform-rakwireless-rui3/releases/download/bsp-<tag>/<package>-<tag>.tar.gz`.

Toolchain: `toolchain-gccarmnoneeabi ~1.90201.0` (GCC 9.2.1, ARM 9-2019-q4-major) — the release the RUI3 Arduino index lists for all three BSPs. With it, a minimal RAK3172 sketch is within 16 bytes of the Arduino build; xPack 9.3.1 added ~4 KB.

To move to a new upstream tag:

```bash
python tools/bsp.py package --tag vX.Y.Z_NNN                       # downloads from GitHub into dist/
python tools/bsp.py package --tag vX.Y.Z_NNN --git-root references # or from local clones
python tools/bsp.py pin --tag vX.Y.Z_NNN --platform-version X.Y.0
python tools/boards.py --tag vX.Y.Z_NNN                            # boards/, platform.json, docs/boards.md
```

Another BSP version (a 5.x beta, an older 4.x) can be used per project without changing the platform: `platform_packages = framework-rui3-nrf52 @ file:///path/to/framework-rui3-nrf52-<tag>.tar.gz`.

## Build & Test

Framework tarballs are found without any published release when they sit in `dist/` next to the platform (where `tools/bsp.py package` writes them). `RUI3_BSP_DIST` (a folder or base URL) takes precedence over both `dist/` and the release URL. PlatformIO only reinstalls a framework when its spec changes, so after rebuilding a tarball with the same name, remove the installed package first.

Prefer `symlink://` when testing a working copy: `file://` copies the whole folder into `~/.platformio/platforms/`, including `references/` (~1.8 GB) and `.git`.

```bash
python tools/bsp.py package --tag v4.3.0_400 --git-root references   # once, into dist/

# In an example's platformio.ini (or pio pkg install -g -p symlink:///path/to/this/repo):
#   platform = symlink:///path/to/this/repo
cd examples/lorawan-otaa
pio run -e rak3172
pio run -e rak4631
pio run -e rak11720
pio run          # all environments

# List boards
pio boards --installed
```

## Upload

nRF52 boards (`upload_protocol = nrfutil`, the default) upload over USB serial, like the Arduino IDE. `pio run -t upload`:
1. Builds `firmware.zip`, the signed DFU package. Its settings (hardware and application version, SoftDevice id, signing key `security/private.key`) are parsed from the nrfutil command in the BSP's `recipe.objcopy.zip.pattern`. An option `nrf52_dfu.package_options()` does not know fails the build.
2. Sends `at+boot`. RUI3 then restarts into its bootloader; this also works when the sketch uses the port for its own data. RUI3 does not implement the 1200-baud touch that `boards.txt` asks the IDE for, so the manifests' `use_1200bps_touch` is upstream data the uploader ignores.
3. Waits 3 s for the port, then runs Nordic's serial DFU (SLIP frames: ping, PRN 0, MTU, init packet, 4 KB data objects), with nrfutil's timings and `rtscts`.

The package is byte-identical to nrfutil's except the signature: nrfutil uses a random ECDSA nonce, `nrf52_dfu.py` an RFC 6979 one, so the same firmware always gives the same package. Standalone use: `python builder/nrf52_dfu.py upload --port /dev/ttyACM0 .pio/build/<env>/firmware.zip`.

STM32 and Apollo3 boards fail `-t upload` with an explicit message until their YMODEM uploader exists.

## Key Reference Files (local only, not in repo)

- `references/RAK-STM32-RUI/`, `references/RAK-nRF52-RUI/`, `references/RAK-APOLLO3-RUI/` — full upstream clones. Their working trees sit on the stale `main` branch; read a release with `git show <tag>:<path>`. Releases come from `RUI_4.2-branch` (4.x) and `RUI_5.0-branch` (5.x beta).
- Each BSP's `boards.txt` / `platform.txt` — the recipes the builder resolves at build time

## Framework packaging

Upstream BSPs have no `package.json`, so `tools/bsp.py package` repackages each tag:
1. Export the tag (GitHub archive or local clone), check that `cores/<core>` exists
2. Apply `tools/bsp_patches.py` — FUOTA guards for `LmhpFragmentation.c`, `LmhpClockSync.c`, `LmhpRemoteMcastSetup.c` (`#ifdef LORA_STACK_104` for `IsTxPending` / `LmHandlerSend`); CRLF is normalised to LF before matching (STM32 BSP uses CRLF)
3. Write `package.json` (`name`, `version` `X.Y.Z+BUILD`, upstream tag and commit)
4. Write a reproducible `.tar.gz` (fixed mtimes and owners) plus `.sha256`, and a `bsp-<tag>.json` index

## Builder Patterns (hard-won lessons)

- **Mirror arduino-cli's layout**: every `.c` / `.cpp` / `.S` under `cores/<core>` goes into the framework library; the variant's files are linked as objects (`BuildSources`), so they override defaults in the core (e.g. nRF52's `app_error` handlers). The only exclusion is `.asm` (a Tasking FreeRTOS port in the STM32 tree). Do not filter lowercase `.s` by glob: on Windows it also matches `.S`.
- **Same-name core sources**: arduino-cli archives core objects by file name with `ar r`, so when two sources share a name only the last one (sorted by path) is linked. `rui3.py` excludes the shadowed copies: nRF52 links the SDK's `modules/nrfx/mdk/system_nrf52840.c` (its `SystemInit()` applies more chip errata), Apollo3 drops mbedtls' `aes.c`.
- **Image name**: PlatformIO's built-in `PROGNAME` is `program`; `main.py` sets `firmware`, as other platforms do, unless the project set one.
- **`buildprog` alias without an action**: the common `env.Alias("buildprog", target, target)` idiom makes SCons execute the targets as commands once there is more than one (Error 126).
- **`.ino` sketches**: PlatformIO only converts `.ino` to C++ for its own `arduino` framework, so `rui3.py` calls `env.ConvertInoToCpp()` itself.
- **Arduino libraries**: PlatformIO's library finder treats `library.properties` libraries as `arduino`-only, so with `framework = rui3` projects need `lib_compat_mode = off` to use them.
- **`-w` only for BSP sources**: the recipes compile with `-w`; it is applied to a cloned env for framework code so the project's own warnings still show.
- **Defines from recipes**: `-D`/`-U` are evaluated in order; quoted values go through `env.StringifyMacro`. Defines that differ between C and C++ (STM32 adds `-DDEBUG` for C++) stay in `CFLAGS` / `CXXFLAGS`.
- **`-l:file.a`** libraries are resolved to full paths and passed as `env.File`; SCons strips `lib`/`.a` from plain names in `LIBS`.
- **`${PROGNAME}` in recipe values**: keep the braces — SCons reads `$PROGNAME.map` as attribute access. The recipe resolver skips `${...}` when expanding Arduino `{placeholders}`.
- **`-fmacro-prefix-map=<package>=.`**: keeps the install path out of `__FILE__` strings (reproducible firmware; ~2 KB flash on nRF52).
- **Builders in `main.py`**: use SCons' `Builder`, not `env.Builder` — `env.Builder` substitutes `$SOURCES` / `$TARGET` immediately, which breaks the verbose-mode string actions.
- **Linker script**: `env.Replace(LDSCRIPT_PATH=full_path)` — never `env.Append(LINKFLAGS=["-T", path])`
- **Assembler**: `AS = arm-none-eabi-gcc` with `-x assembler-with-cpp` (from the BSP recipe; .S files use the C preprocessor)
- **Double-call pitfall**: Never call framework scripts manually from `builder/main.py` — `BuildProgram()` already calls `BuildFrameworks()`
